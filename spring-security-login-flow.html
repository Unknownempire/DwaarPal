Follow the phone-and-password check from the mobile app, through your DwaarPal classes and Spring Security, to the JWT flow we are building.

3. LoginService asks Spring to authenticate

LoginService.authenticate() packages phone and submitted password in a UsernamePasswordAuthenticationToken, then calls authenticationManager.authenticate(...). At this point the submitted credentials are not yet trusted.

4. AuthenticationManager delegates the work

AuthenticationManager is Spring Security’s interface. Your configuration exposes Spring’s configured manager as a bean. Under the usual username/password setup, Spring uses a ProviderManager and a DaoAuthenticationProvider.

DwaarPal exposes the manager in security/SecurityConfig.java; provider implementation is Spring Security code, not a DwaarPal class.
↓

5. DaoAuthenticationProvider asks for the account

The provider calls Spring’s UserDetailsService.loadUserByUsername(phone). It needs the stored password hash, account status, and authorities to finish the check.

This is the Spring Security component that connects account lookup to password verification.
↓

6. DwaarPalUserDetailsService adapts DwaarPal’s user

Because it is a Spring bean and implements Spring’s UserDetailsService, it can be used by the provider. It looks up the user by phone and returns Spring’s UserDetails: phone as username, stored BCrypt hash, role authority, and enabled/disabled account state.

DwaarPal file: src/main/java/com/pranav/society_vehicle_manager/security/DwaarPalUserDetailsService.java
↓

7. UserRepository reads the account

findByPhone(phone) retrieves the matching DwaarPal User from PostgreSQL. The service converts that entity into Spring Security’s smaller account view.

DwaarPal file: src/main/java/com/pranav/society_vehicle_manager/repository/UserRepository.java; entity: entity/User.java
↓

8. PasswordEncoder checks the password

DaoAuthenticationProvider compares the submitted raw password to the stored BCrypt hash by using PasswordEncoder.matches(...). It does not decrypt the hash. The provider also rejects an account marked disabled.

The BCrypt encoder bean is in security/SecurityConfig.java; registration uses the same bean through service/UserService.java.
↓

Credentials valid

Spring returns an authenticated Authentication containing the verified principal and authorities. LoginService returns this result.

Credentials invalid / account inactive

Spring rejects authentication. Later, the API should map this safely to a generic 401 Unauthorized response without revealing whether the phone exists.

B. JWT issuance and later requests

9. Create a JWT after successful login

A future token service will take the authenticated identity and ask JwtEncoder to sign a token with an expiry. The API will return it in LoginResponse as a Bearer access token.

Not connected yet: LoginService currently returns Authentication, not a JWT. LoginResponse exists but no controller returns it.
↓

10. Mobile app sends the token later

For protected requests, the app will send the token in the HTTP Authorization: Bearer … header. The token is signed, not encrypted, so it must not contain passwords or secrets.

↓

11. SecurityFilterChain validates the bearer token

The future filter-chain configuration will enable OAuth2 Resource Server JWT support. Spring will call JwtDecoder to verify the signature and expiry, then establish the authenticated identity for the request.

Not connected yet: no DwaarPal SecurityFilterChain is configured.
↓

12. Authorization protects DwaarPal resources

After identity is established, request rules and service checks decide what the person may do. DwaarPal must still check society membership and ownership; a role such as ADMIN alone does not grant access to every society.

Still to do: endpoint rules and replacing request-supplied actor IDs with authenticated identity.

Quick notes: who does what?

UserService

Registers residents and hashes a new password before saving it. It does not log users in.

LoginService

Submits login credentials to Spring’s manager. It does not look up the user or compare hashes itself.

UserDetailsService

Loads an existing account and translates it to Spring Security’s account format. It does not verify the submitted password.

DaoAuthenticationProvider

Spring’s provider that coordinates account loading and password checking for username/password authentication.

AuthenticationManager

Spring’s coordinator. DwaarPal exposes it as a bean so the login service can ask Spring to authenticate credentials.

JwtEncoder / JwtDecoder

Encoder signs the future access token; decoder verifies tokens on future requests. Both use the configured secret key for HS256.

Implementation status

In place: phone lookup, user-details adapter, BCrypt bean, AuthenticationManager bean, login request/response DTOs, LoginService credential submission, and JWT key/encoder/decoder beans in the current files.

Still needed: login controller, JWT creation service, wiring token generation into successful login, SecurityFilterChain with bearer JWT validation, endpoint authorization, and using the authenticated identity throughout protected operations.

The encoder and decoder beans are available as tools, but no login endpoint currently calls the encoder and no filter chain currently calls the decoder.
